## 三、赛道 1：通用网页监控 —— changedetection.io（架构必学）

**它是什么**：最主流的"网页变化检测"开源项目，33k+ 星，Apache-2.0 可自由商用。盯着一个 URL，定时抓取，**内容变了就发通知**（支持邮件/Telegram/Webhook 等）。

**你能学到的核心架构（这是整个监控类通用范式）**：

1. **一次一条快照，永不覆盖** —— 每次抓取存一份完整快照（历史表追加式），不是把旧的盖掉。
2. **变化 = 和"上一次"做 diff** —— 存的是快照，变化是"算出来"的，不是"存出来"的。
3. **历史可回放** —— 所有快照都留着，随时看任意一次长什么样。
4. **可选"过滤"只盯局部** —— 支持 CSS/XPath 选择器，只监控某个元素（比如只盯价格那个 span），而不是整页。

**和你的对照**：
- 你现在 `tracking` 表的问题正是第 1、2 点没做到 —— 只存了 `prev_*` 三个字段，**覆盖式**，历史丢了。
- 你要的"历史变化"，就是它第 1/3 点。**架构上照抄它没错。**

**但它不懂亚马逊**：它只看"这段文本变了没"，**不知道什么是 BuyBox、变体、评价星级**。所以它解决"怎么存历史、怎么对比"，不解决"对比哪些亚马逊字段"。

## 四、赛道 2：电商价格追踪 —— Discount-Bandit（产品思路必学）

**它是什么**：Multi-User Selfhosted 价格追踪，支持 Amazon / AliExpress / eBay / Walmart / Newegg 等 + 自定义站点。PHP + Laravel + FilamentPHP。733★。

**你能学到的产品思路（比架构更值钱）**：

1. **"按规则判断变化，只报命中的"** —— 它核心理念是用户设一组条件（价格低于 X / 折扣达到 Y% / 有货），**只有条件命中才通知**。不是"页面字变了就吵你"，而是"满足我的规则才叫我"。
2. **关注的是结构化字段，不是整页文本** —— 价格、库存、折扣，这些是"解析出来的业务字段"，不是 diff 出来的文本。
3. **多站点用一套抽象** —— 不同平台（Amazon/淘宝/eBay）通过适配器抽象成统一字段，上层规则通用。

**和你的对照（极其贴合）**：
- 你列的"价格被改、标题被改、BuyBox 被改、评价新增、变体掉了、评分掉了、首页差评"——**每一条都是"结构化字段 + 规则命中"**，正是 Discount-Bandit 的思路。
- 你的"加基线，只报和基线的差异"——**这就是它"用户设规则"的细化**，比"每次都报"更符合卖家判断。
- 技术栈不匹配（PHP），**代码不能搬，但产品设计思路是教科书级的**。

## 六、赛道 2.5：MCP 取数（AI 时代主流，社区极活跃）

**这是上一轮遗漏、且极其重要的一块。** 用户指正得对：现在"监控/取数"已经分化出主流的两条路，MCP（Model Context Protocol）是之一。

**MCP 是什么**：一种开放协议，让 AI（Claude 等）通过标准接口去**调用外部数据源/工具**——一个"MCP server"就是一个数据/动作的封装。对监控场景，意义是：**你不用自己写解析器，接一个现成的 MCP server 就能拿到结构化数据**（商品价格、库存、评价、详情），AI 再基于这些数据做判断。

**两条主流路径（用户总结，完全准确）**：

| 路径 | 做法 | 代表 |
|------|------|------|
| **A. 接 MCP 拿数据** | 用/自建 MCP server 取结构化商品数据，交给 AI 判断 | Fewsats/amazon-mcp、idealo/mcp-server-guide 等 |
| **B. 纯手搓查页面** | 自己写 Playwright/Selenium 解析页面，自研判定 | AmReview 现在的 `engine.py` |

**已查证的相关开源（今日实时）**：

| 仓库 | Star | 语言 | 用途 |
|------|------|------|------|
| Fewsats/amazon-mcp | 80 | Python | Amazon MCP，搜/买商品（L402 支付协议） |
| appcypher/awesome-mcp-servers | 5.8k | - | MCP 服务器聚合清单（导航用） |
| MentionNetwork/awesome-agentic-commerce | 61 | - | 电商方向的 agentic commerce 资源清单 |
| idealo/mcp-server-guide | 15 | - | 欧洲 6 市场比价/找 Deal 的 MCP |
| eduard256/ozon-mcp-server | 45 | JS | Ozon 市场 MCP（拿商品详情/价格/评价） |

> 附：`wong2/awesome-mcp-servers`(4.3k★)、`YuzeHao2023/Awesome-MCP-Servers`(1.1k★) 也值得收藏，当你要找某个平台 MCP 时先查这些清单。

**对你的意义（重要判断）**：
- 你**不必再"从零手搓全部解析层"**——如果 Amazon 有合用的 MCP server（数据够全、更新够快、能拿价格/评价/变体/排名），**路径 A 能省掉大量爬虫工作**，尤其"AI 辅助判断异常"这件事 MCP 天然契合。
- 但要注意：**Amazon 商品数据的 MCP server 良莠不齐**——有的是接**付费 API**（如 Keepa API、ScrapingBee），有的是**半吊子爬虫**，还有的是**广告/购买接口**（如 Fewsats 是 L402 购买）。**用之前要核实数据源、更新频率、是否收费**，别接到一个要持续花钱买额度的。
- **判断你在哪条路径的决策点**：a) 你要的字段（BuyBox 归属、变体集合、首页差评、BSR）**现成 MCP 是否都能给**？b) 是否接受付费用第三方数据源？c) 数据实时性/频率要求。决定后选 A 或 B，或 A 取数 + B 兜底混合。

## 八、你自己的需求 → 设计映射（把上面的范式落到 AmReview）

### 8.1 为什么你的"异常监控"和"通用监控"不一样

| | 通用监控 (changedetection.io) | 你的需求 (卖家异常监控) |
|---|---|---|
| 判断"变了没" | 文本 diff | **字段规则命中** |
| 通知时机 | 每次变化就报 | **只报"和基线不同"的** |
| 懂亚马逊语义 | 不懂 | **必须懂** (BuyBox/变体/评价) |
| 频率 | 自己设 | 每小时(你的 cron) |

### 8.2 你要的指标，实际上分两类（你自己总结的，很准）

- **基础信息类（相对稳定）**：标题、图片、BuyBox、Dp（直达链接/父ASIN?）、五点
  - 特点：不常变 → **变化本身就是异常**，适合低频对比、阈值宽松
- **动态变化类（波动大）**：评价数、评分、DealTag、价格、首页差评、排名、BuyBox
  - 特点：合理波动是常态 → **必须设基线 + 阈值**，否则天天误报

**设计含义**：两类指标要**分开处理**。稳定类可以用"和上次比 + 简单 diff"；动态类要**基线 + 阈值 + 确认机制**。这也解释了为什么你一定要"加基线"。

### 8.3 勾选要监控哪些指标

你要的"勾选哪些指标"，本质是**把异常规则做成可配置**。成熟做法是"**每个 ASIN 一组监控开关**"，而不是全局统一 —— 不同链接关注点不同（有的只看价格，有的还要盯首页差评）。对应到 UI：每行一个配置入口，或批量默认 + 单条覆盖。

### 8.4 展示：上百链、多国、如何优雅

你的核心诉求是"上百条、六国、怎么一眼看到异常"。参考监控类产品的通用做法：

- **异常优先，正常折叠**：今天的异常项**顶到最前面**，每条带**异常类型徽标**（如 `⚠ 价格 -12%` / `⚠ 丢 BuyBox` / `⚠ 新增差评×2`）。正常项收进"全部正常"折叠区。
- **看板式摘要**：顶部一行"今日 12 条，3 异常"，异常按**严重度**排（丢 BuyBox / 价格剧烈 > 差评 > 小幅波动）。
- **点开看证据**：点异常行 → 弹窗看这条的**变化史 + 每次变化的字段值**，作为"要不要处理"的判断依据（这就是你最初问的"历史变化"，但它服务异常判断）。
- **国家维度**：上百链跨六国，顶部按站点筛选，异常看板默认聚合所有站点，可切单站。

### 8.5 定时的实现：内部 Cron

你强调"本项目内部自己跑，不用宝塔/GitHub Actions"。**你后来说的"宝塔的计划任务是定时去检查 cron 是否要启动"——这是对的，也是最省心的做法**，值得展开：

- **推荐**：宝塔「计划任务」里加一条**每分钟/每小时检查**这个监控脚本是否在跑（cron 守护），没跑就拉起。这就是"看门狗"模式，进程死掉能自动恢复，比"脚本内 while True"更抗崩溃——因为脚本内循环一旦抛异常退出，没人拉它。
- **纯进程内调度**（`schedule` / `APScheduler` + `threading`）也能做，但风险是 Streamlit 重跑模型下，**调度循环若在页面文件里会阻塞页面**；要单独起 `run_monitor.py` 子进程才干净。宝塔 cron 恰好解决了"谁保证它一直活着"。
- 结论：**用宝塔计划任务做"守护"，用 Python 脚本做"实际抓取 + 判定"**，两层分工，最稳。
- **关键**：如果项目是 Streamlit 单进程，调度循环要**独立于页面渲染**——用 `threading` 或单独起一个 `python run_monitor.py` 子进程，避免阻塞页面。
- 现在 `engine.py` 已有 `check_batch`，监控复用这套抓取逻辑 + 已登录的小号账号。

### 8.6 小号复用

你问"查评价用的小号，能否复用查链接信息"——**可以，而且应该**。同一套 Playwright 登录态（`storage_state.json`）既能访问评价页也能访问产品页，反爬风险也更低（同一个账号指纹）。建议：**登录态共享、抓取隔离**——评价检测和链接监控共用"账号登录态存储"，各自维护独立的定时任务和频率，避免同一个小号同时高频跑两种任务而被封。

| 3 | 引擎解封 `check_products`，解析亚马逊字段(价格/评分/评价数/BuyBox/变体/首页星级) | Keepa 指标清单 |
| 4 | 规则层：差异检测 + 可勾选指标 + 基线/阈值 | Discount-Bandit |
| 5 | 定时：宝塔 cron 守护 + Python 脚本抓取 | 看门狗模式 |
| 6 | 看板 UI：异常优先 + 点开看变化史 + 钉钉通知 | 监控类产品通用范式 |

> 核心判断修正：**没有一个能整包搬进来**。但"懂亚马逊语义的异常监控"**不是市场空白**——**取数层有大量可选**（自研爬虫 / SP-API / MCP），监控架构（changedetection.io）、产品思路（Discount-Bandit）也都成熟可直接借鉴。缺的只是"**懂亚马逊语义的判定层**"（BuyBox/变体/首页差评这些该怎么判定异常），**这是你的 Know-how，需要自研**。数据来源可自研或 SP-API，判定规则必须自己写。

## 0. 一句话架构

```
采集(可替换) → 结构化快照(追加式) → 规则判定(你的Know-how) → 通知(钉钉) + 看板(异常优先)
```

**核心设计原则：采集层与判定层解耦。** 采集是易变、可替换的；**判定层才是你这个产品的真正资产**。这点是推倒重来最该先定死的。

---

## 1. 从开源项目学到的 4 条架构原则（为什么这样设计）

| # | 原则 | 从哪学 | 为什么 |
|---|------|--------|--------|
| 1 | **采集与判定解耦** | changedetection.io / Discount-Bandit | Amazon 改页面结构 → 只重写采集，业务规则不动；换数据源（MCP⇄自研）只换采集 |
| 2 | **快照追加而非覆盖** | changedetection.io | 历史可回放；你现在 `tracking` 只存 `prev_*` 覆盖式，历史丢失，必须改 |
| 3 | **规则命中才报，而非全报** | Discount-Bandit + 你的基线 | 卖家要的是"是否异常"，不是"任何变化都吵"；否则自己改价天天误报 |
| 4 | **结构化字段，而非文本 diff** | Keepa / Discount-Bandit | 懂 BuyBox/变体/首页差评**语义**你才有价值，整页文本 diff 是通用监控干的事 |

> 关键洞察：这 4 条是这套系统"万丈高楼平地起"的地基。**第 2、3 条是推倒重来的核心**——你的现状是"覆盖式 + 全报"，必须改成"追加式 + 按基线规则报"。

## 2. 模块划分（建议目录，独立于现有 engine.py）

```
monitor/
├── __init__.py
├── model.py        # ProductProfile(结构化字段) / SnapshotRecord —— 数据契约
├── address.py      # 采集接口 + 适配器: Playwright(自研) / MCP(第三方) / Keepa(付费API)
├── store.py        # SQLite: profiles / snapshots / anomalies 三张表, 追加式写
├── rules.py        # 判定引擎: 每指标开关/类型/阈值/基线逻辑 —— 你的核心 Know-how
├── baseline.py     # 基线管理: 首次自动设基点 / 用户"确认无误"后前移
├── notify.py       # 钉钉 webhook: 异常格式化 + 严重度 + 去重
├── scheduler.py    # 被宝塔 cron 调用的入口: 跑一轮 pipeline
└── board.py        # Streamlit 看板: 异常优先 + 点开看历史 + 站点筛选
```

> 可与现有 `engine.py`（评价检测）共存：它们**共用登录态/小号 + Playwright 底层**，但业务逻辑独立。现有 `review` 检测保留，新增的 `link` 监控独立成包，别混在一起。

## 3. 数据模型（SQLite 三张表）

### 3.1 `profiles`（一条 = 一个要监控的 ASIN）
| 字段 | 说明 |
|------|------|
| asin / domain / url | 主键 + 站点 |
| parent_asin / title | 稳定身份 |
| monitor_enabled | 是否监控 |
| metric_config (JSON) | 每指标开关 + 阈值（勾选指标的落点） |
| baseline_snapshot_id | 基点在哪个快照上 |
| last_checked_at | 最近检查时间 |

### 3.2 `snapshots`（追加式，一条 = 一次检查快照）★ 核心
| 字段 | 说明 |
|------|------|
| id / asin / domain / checked_at | 标识 + 时间 |
| title / image_url / buybox / variations(JSON) | 稳定类字段值 |
| price / price_value / currency / rating / review_count / bsr / deal_tag | 动态类字段值 |
| home_reviews(JSON) | 首页评论星级分布 / 最近差评 |

> **这是 changedetection.io 的"快照不覆盖"落地**：每次检查都 insert 一行，ASIN 历史 = 按时间查所有行。**删掉**现在 `tracking` 表里的 `prev_*` 字段——历史由 snapshots 算出，不再存"上一版"。

### 3.3 `anomalies`（检测出的异常，用于去重/通知/已读）
| 字段 | 说明 |
|------|------|
| id / asin / domain / metric / change_type | 异常类型（如 price_down / lost_buybox / new_bad_review） |
| old_value / new_value / severity / checked_at | 前后值 + 严重度 |
| notified / confirmed | 是否已推钉钉 / 用户是否确认 |

## 4. 判定引擎（两类指标 + 基线逻辑）★ 价值中心

### 4.1 两类指标（你的总结正确，分开处理）

| 类别 | 指标 | 对比对象 | 判异常逻辑 |
|------|------|---------|-----------|
| **稳定类** | 标题 / 图片 / BuyBox归属 / 父ASIN / 变体集合 | **上次快照** | 任何变化 = 异常（这些不该自己变） |
| **动态类** | 价格 / 评分 / 评价数 / DealTag / BSR排名 / 首页差评 | **基线** + 阈值 | 变化超阈值才报（避免正常波动误报） |

> 例子：动态类价格，`|当前价-基线价|/基线价 > 5%` 才报；首页差评，本次**新增 N 条 ≤2星** 才报。每指标阈值可配。

### 4.2 基线语义（卖家场景最关键，比"与上次比"强）
- 每个 ASIN 有一个 `baseline_snapshot_id`（"这是正常的"基准）。
- **判定 = 当前快照 对比 基线**（不是对比上次）→ 所以你**自己改价/改标题不会误报**。
- 你在看板点某条异常"确认无误" → **基线前移**到当前快照，之后以此为基准。
- 稳定类例外：仍对比上次（敏感），因为标题/图片/BuyBox 自己不该动。

## 5. 采集层：自研 Playwright（已拍板）＋ SP-API 兜底（可选）

> **User 决策（2026-08-23）**：**确定走"自研 Playwright 为主"，不用 MCP**（用户已有领星 MCP，但不用作商品数据源）。采集做成接口，后续可用 SP-API 兜底。

| | 方案 B：自研 Playwright（✅ 已选） | 备选：SP-API（官方兜底） | MCP（❌ 不选） |
|---|---|---|---|
| 原理 | 你现有 engine.py 的路子 + 已登录小号 | Amazon 官方 Selling Partner API | 接第三方 MCP server |
| 你要的字段 | BuyBox/变体/首页差评 **全可控** | 价格/BuyBox 官方字段 | BuyBox/变体/首页差评最弱 |
| 成本 | 免费，防反爬 + 限速 | 需申请 SP-API 权限 | 很多付费 |
| 数据实时性 | 你控制（每小时） | 官方推送 | 看服务商 |

**为何自研为主**：
1. 你**要的恰是 MCP 最弱的字段**（BuyBox、变体、首页差评），这些得自己解析；
2. 你**已有** Playwright + 六国登录小号，复用成本低，且你明确"不想用 MCP 当商品数据源"；
3. 你**自己控制**每小时频率，不被第三方节奏绑死；
4. **关键**：采集做成接口（`address.py`），B 不稳的字段（如价格/BuyBox）**后续可用 SP-API 兜底**，不用推倒重来。

> **反爬提示（配合作者"先小批量 + 放宽频率"的决策）**：每小时 × 上百链 × 六国是较大流量。**必须限速 + 复用登录态 + 必要时代理**。按用户决策：**初始放宽到 2-4 小时 + 先小批量验收入，再梯度加密**，别一上来每小时全量（IP 会热）。

## 6. 调度与通知

- **调度（看门狗模式，你判断正确）**：宝塔「计划任务」每分钟/每小时检查 `run_monitor.py` 是否在跑，没跑就拉起。脚本内一次跑一轮 pipeline，跑完退出。比"脚本内 while True"抗崩溃——进程死了有人拉。
- **通知（钉钉机器人）**：`notify.py` 命中异常 → 钉钉 webhook 推送，内容含：ASIN + 标题 + 站点 + 异常类型 + 前后值 + 严重度 + 复盘链接。加**去重**（同一异常未确认不重复推）+ **严重度分级**（丢 BuyBox/价格剧烈 > 差评 > 小波动）。

---

## 7. 看板展示（上百链、六国、一眼看异常）

- **异常优先，正常折叠**：今天异常项**顶到最前**，每条带**异常类型徽标**（`⚠ 价格 -12%` / `⚠ 丢 BuyBox` / `⚠ 新增差评×2`），正常项收进"全部正常"折叠区。
- **看板摘要**：顶部"今日 N 条，M 异常"，按**严重度**排。
- **点开看证据**：点异常行 → 弹窗看这条的**变化史**（历次快照值）+ 当前 vs 基线对比，作为"要不要处理"依据。
- **站点筛选**：上百链跨六国，顶部按站点筛选，默认聚合所有站点。
- **基线确认**：异常行给"确认无误→前移基线"按钮，这是闭环的关键操作。

## 8. 分阶段落地（建议顺序）

| 阶段 | 做什么 | 目的 | 碰真实抓取? |
|------|--------|------|------------|
| 1 | 建 monitor 包 + 三表 + 采集接口 + ProductProfile 契约 | 打地基：数据模型和模块边界 | 否 |
| 2 | rules 判定引擎 + baseline（先用现有 mock 数据造多条历史测） | 验证"异常判定 + 基线"逻辑 | 否 |
| 3 | 看板 UI：异常优先 + 点开历史 + 基线确认 | 验证展示交互 | 否 |
| 4 | Playwright 采集适配器（真抓1-2条，跑通 BuyBox/变体/首页差评） | 打通真实数据 | 是（1-2条） |
| 5 | 钉钉通知 + 宝塔 cron 守护 + 梯度扩到全量 | 上线运营 | 是（全量） |

> 阶段 1-3 不碰真实抓取，用 mock 造历史，风险低、见效快；阶段 4 才是真正的"解析层攻坚"。**先能把结构和交互跑通，再啃最难的抓取解析。**

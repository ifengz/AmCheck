# 服务器依赖清单修复指令（给宝塔 AI 执行）

## 问题一句话

`code/requirements.lock.txt` 曾停在 Streamlit 时代（44 行），**缺 nicegui /
fastapi / uvicorn / starlette / python-socketio / dingtalk-stream**；
而 `code/start.sh` 首次建 venv 时**优先装 lock 文件** ——
新机器跑 `start.sh` 会装完一堆 Streamlit 依赖后才在启动时
`ModuleNotFoundError: nicegui`。

生产**没有**受影响：`deploy/deploy.sh` 装的是 `requirements.txt`，
所以线上一直是好的；坏的只有「新机器 / 新克隆的首次初始化」这条路径。

本地已修复并实测（见文末），**现在这一步只是让服务器确认线上环境正常**。

## 三条硬约束（务必先读，否则会白干）

1. **不要修改 `/www/wwwroot/amcheck_git/` 下任何被 git 跟踪的文件。**
   `deploy.sh` 每次部署都执行 `git reset --hard origin/main`，
   服务器上的改动会被静默冲掉。所有修复必须走 git（本地改 → push）。
2. **不要动生产 `.venv`。** 所有验证都在 `/tmp` 下的一次性 venv 里做。
3. **不要重启服务、不要重跑 deploy.sh。** 本次只做「读 + 隔离验证」。

## 附一：lock 的两个失效模式（这次都修了）

**模式 1：内容过期。** lock 停在 Streamlit 时代，整个 NiceGUI 栈都不在里面。
已重新生成（88 行，逐个校验过 PyPI 上存在）。

**模式 2：Python 版本不匹配。** 这个更隐蔽 —— lock 是在「某个 Python 版本 +
某个平台」下 `pip freeze` 出来的，换版本可能根本装不上。
实测把当时的 lock 装到 Python 3.13：`numpy==2.0.2` 没有 3.13 的轮子，
pip 转去源码编译 → `metadata-generation-failed`。

numpy 每个大版本的 Python 支持窗口都不一样：

| numpy | 支持的 Python |
|---|---|
| 2.0.x | 3.9 ~ 3.12 |
| 2.1.x | 3.10 ~ 3.13 |
| 2.3.x | 3.11 ~ 3.14 |

**没有任何单一版本能同时覆盖 3.9 和 3.13**，所以 lock 里改成了两条带标记的 pin：

```
numpy==2.0.2; python_version < "3.13"
numpy==2.1.3; python_version >= "3.13"
```

numpy 是 `streamlit → pandas` 带进来的传递依赖，主界面（NiceGUI）不需要它，
但 legacy 界面要，所以不能删，只能分版本锁。

## 附二：本地实测结果（全新一次性 venv，各跑一次真实安装）

| 清单 | 3.9 | 3.10 | 3.11 | 3.12 | 3.13 |
|---|---|---|---|---|---|
| `requirements.lock.txt`（修复后） | ✅ 实装通过 | ✅ | ✅ | ✅ 实装通过 | ✅ 实装通过（numpy 2.1.3） |
| `requirements.txt` | — | — | — | — | ✅ 实装通过 |

3.10 / 3.11 是**元数据分析**结论（查 PyPI 每个 pin 有没有 Linux 轮子），
3.9 / 3.12 / 3.13 是**真实安装**验证过的。

**结论：修复后的 lock 在 Python 3.9 ~ 3.13 全都能装**，
所以服务器是哪个版本都不影响，第一步只是核对。

> 方法学提醒：分析轮子兼容性时不能只看 `cp3XX` 标签。
> `pkg-1.0-py3-none-manylinux…whl`（playwright 这种）是**版本无关**的；
> `pkg-1.0-cp39-abi3-manylinux…whl`（tornado 这种）是**稳定 ABI**，
> 3.9 一次编译、3.9 及以后全通用。只认 cp3XX 会把这两类误判成「装不上」。

## 附三：这次对仓库做的改动

| 文件 | 改动 |
|---|---|
| `code/requirements.lock.txt` | 重新生成；numpy 改为按 Python 版本分两条 pin |
| `code/gen_lock.sh` | **新增**：可复现地重新生成 lock（排除 lint 工具、固定排序、内置 numpy 分版本规则） |
| `code/requirements.txt` | 补 `packaging` / `pillow`；加注释说明两份清单的关系 |
| `code/start.sh` | lock 装失败**自动退回** `requirements.txt`；装完做依赖自检 |
| `code/tests/test_requirements.py` | 10 例：声明→锁覆盖、核心栈在锁里、精确 pin 且排序稳定、多 pin 标记齐全且互斥、锁与实测环境不脱节、第三方 import 必须已声明 |

两个关键设计：

- **`start.sh` 的退回分支**：以后 lock 再烂也不会让新机器起不来，最坏只是退回浮动版本。
- **`gen_lock.sh`**：lock 之所以会腐烂，就是因为没有「重新生成」的固定路径。
  现在有脚本了，而且 numpy 的分版本规则写在脚本里，不会再漏。

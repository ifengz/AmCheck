# 终版方案：单条评价 Permalink 批量检测

> 日期：2026-08-14（第四轮 · 需求最终收敛）
> **本文件是项目唯一权威方案**，前三份文档降级为背景资料。

---

## 一、需求（最终确认，不再变）

**一次粘贴约 20 条 Amazon 评价 permalink**（形如 `https://www.amazon.com/gp/customer-reviews/R1XXXXXXX/`），工具逐条访问，输出每条评价的：

| 输出项 | 说明 |
|--------|------|
| 状态 | ✅ 正常 / 🐕 已被删（变狗）/ 🤖 被反爬拦截 / ❓ 未知 |
| 星级 | 1~5 星（读自评价页 star rating） |
| 证据 | 评价标题、作者、日期（证明"还是原来那条"）、页面截图 |

**明确排除**：不查产品页评价列表、不用 Keepa（它不覆盖单条评价）、不做大规模监控（20 条/次是纳米规模）。

---

## 二、实测证据（2026-08-14，本机两轮实测）

### 第一轮：curl 裸 HTTP

| 实验 | 结果 | 结论 |
|------|------|------|
| `curl` 假 review ID | `307 → /edgex/guard/rx?...` | Amazon 有边缘反爬守卫（edgex guard），**纯 HTTP 请求必被拦** |
| `curl` 产品页 ASIN | `404`（守卫拦截的伪装） | 裸 requests 结果不可信 |
| 本机 → amazon.com 延迟 | 0.9~2.8s | 网络畅通，无需代理 |

### 第二轮：Playwright 驱动本机 Chrome（headless，无任何 stealth 加持）⭐

| 实验 | 结果 | 判定 |
|------|------|------|
| 假 review ID `/gp/customer-reviews/AFAKEID12345/` | **HTTP 404，title="Page Not Found"，未被 guard 拦** | ✅ **edgex guard 被真浏览器穿透**（连隐身补丁都不需要） |
| 真 review ID（老链接） | HTTP 200 但**重定向到 `ap/signin` 登录页** | ⚠️ **新墙：登录墙**——有效评价页需要登录态才能看 |
| `/review/RXXX` 短格式 | 同样跳登录页 | 登录墙覆盖所有评价 URL 格式 |
| `/product-reviews/ASIN` | 同样跳登录页 | 同上 |

### 第四轮实测:代码落地验证(2026-08-14 下午,引擎实现后)

| 实验 | 结果 | 判定 |
|------|------|---------|
| `.com` 假 ID `AFAKEID12345` | HTTP 404 "Page Not Found" | 🐕 已删,判定与上午一致 ✅ |
| `.com.au` R2SX0V488I8HE6(上午曾 404) | 全新档案:guard 破后 → 登录墙;带匿名 session cookie:直接登录墙;portal/短格式/带 referer 变体:全部登录墙 | ⚠️ **.com.au 匿名 404 判定已不可靠**——Amazon 边缘按会话分桶,匿名访客连"删没删"都可能锁进登录墙 |

**第四轮修正**:第三轮"404 判定不需要登录态"降级为**时灵时不灵**。结论收敛为:**登录态为唯一可靠路径,所有站点一律先引导登录**;引擎中 `/ap/signin` 分支先匿名热身复访一次(给 guard 分桶留活口),仍弹登录才报 🍪。`.com` 假 ID 404 仍稳定可判,作为免登录的兜底判定保留。

---

### 两轮实测的最终结论

1. **edgex guard（反爬守卫）：✅ 已解** —— 普通 Playwright + 本机 Chrome headless 即可穿过，`patchright/camoufox` 留作后备升级项
2. **登录墙：⚠️ 必须处理** —— 评价页对无 cookie 访客一律弹登录。解法：**持久化浏览器上下文 + 一次性人工登录 Amazon 买家号**（保存 `storage_state.json`，之后全程自动）。注意：
   - 用**专用小号**登录，别用主力买家账号
   - 好消息：**已删评价（404）不需要登录态就能判**——被 guard 拦和登录墙只发生在"评价还活着"的路径上，说明 404 判定在认证之前完成
3. **判定规则当场验证成功**：假 ID → `404 + "Page Not Found"`，与第三节状态机完全吻合
4. 星级/标题/作者提取需在**登录态**下进行

### 第三轮实测：两条真实评价链接（用户样本，2026-08-14）

| 链接 | 过程 | 最终判定 |
|------|------|---------|
| `amazon.com.au` R2SX0V488I8HE6 | 首次访问遇 **"Server Busy"**（软拦截，非结论）→ 对策生效：**热身首页拿 session cookie 后重访** → `HTTP 404, "Page Not Found", "Looking for something?"` | 🐕 **评价已删（变狗）** |
| `amazon.in` RQWX9100MIJ7A | portal 格式 / 经典 `/gp/customer-reviews/` 格式 / 带不带 session cookie，**全部弹登录墙** | ⏳ **无法判定——印度站把所有评价页锁在登录后** |

第三轮新增经验（已纳入设计）：
1. **"Server Busy" 页 ≠ 结论**，是软拦截——状态机必须加此分支：热身首页 → 重试（本例一次即破）
2. **站点差异坐实**：`.com/.com.au` 无登录可判"删没删"；`.in` 连删没删都锁在登录后 → **登录态从可选升级为必配**
3. URL 预处理正则需兼容 portal 新格式：`/portal/customer-reviews/srp/-/(\w+)/`

## 三、判定规则（核心逻辑）

对每条评价 permalink，浏览器打开后按优先级判定：

### 状态机

```
打开链接（携带已登录 storage_state）
  │
  ├─ 跳到 /ap/signin → 🍪 登录态失效（重新人工登录或换号）
  │
  ├─ 页面含 "Server Busy"（软拦截，非结论）→ 🔄 热身首页拿cookie后重试（最多3次）
  │
  ├─ 最终 URL 含 /edgex/guard 或 captcha → 🤖 被拦截（退避重试，最多3次）
  │
  ├─ HTTP 404 / title="Page Not Found"（已实测验证 ✅）
  │   或页面文本含 "Sorry, we couldn't find that page" / "Looking for something?"
  │   或图片路径含 /dogs/（狗狗图）          → 🐕 评价已被删（变狗）
  │
  ├─ 页面含 div[data-hook="review"] 完整评价块 → ✅ 正常，继续提取字段
  │
  └─ 其他                                  → ❓ 未知（截图存档，人工/AI复核）
```

### ✅ 正常时提取字段（Amazon review permalink 页选择器）

```python
星级:    i[data-hook="review-star-rating"] 的 class（如 a-star-4 → 4星）
        或 span[data-hook="review-star-rating"] 的 aria-label / title
标题:    a[data-hook="review-title"] 内 span 最后一个子节点
作者:    span.a-profile-name 或 div[data-hook="review-user"] 
日期:    span[data-hook="review-date"]
正文:    span[data-hook="review-body"]
VP标识:  span[data-hook="avp-badge"]（Verified Purchase）
```

> 这些选择器来自 Amazon review 页长期稳定的 `data-hook` 体系（2017 年至今微改），比 CSS class 稳得多。多选择器 fallback 写法参考文档 01 的 `find_with_fallbacks()`。

### 🐕「变狗」的判定信号（组合拳，任中其二即判删）

1. HTTP 404
2. `<title>` 含 "Page Not Found"
3. 页面文本含 "Sorry, we couldn't find that page"
4. 图片资源路径含 `/dogs/`（Amazon 著名狗狗 404 图）
5. 无 `div[data-hook="review"]` 且非 captcha 页

> 注意区分：**评价被删 = 该 review ID 的 404**；**整个 listing 被删时 review permalink 也会 404**。两者对卖家都是"变狗"，可不细分；如需细分，可加一步检查对应 ASIN 产品页（可选功能）。

## 四、最终架构（极简版，配宝塔）

```
Streamlit 网页（宝塔 Python 项目管理器）
├─ 输入页：textarea 粘贴 20 条链接 + 「开始检测」按钮 + 进度条
├─ 结果页：表格（状态 | 星级 | 标题 | 作者 | 日期 | 截图链接）+ 一键导出 CSV
└─ 证据：变狗/未知项自动存截图到 ./screenshots/

检测引擎 check.py
├─ patchright(headless) 逐条访问（3~5s 限速，拦截则退避重试）
├─ 状态机判定（第三节规则）
└─ ❓未知项 → 调 GLM-4V 看截图二次确认（可选开关）

SQLite（可选）：检测历史留存，同一链接可看"上次还在/这次没了"
```

**技术栈合计**：`streamlit + playwright(驱动本机Chrome, 实测已过守卫) + storage_state登录态 + sqlite3`，加上可选的 GLM-4V 兜底。patchright/camoufox 仅在被识别时升级。
**代码量预估**：核心引擎 ~150 行，页面 ~100 行。真正的纳米项目。

## 五、登录态设计（不干扰日常浏览的隔离方案）

### 5.1 隔离原则

工具使用**独立档案目录的专属浏览器实例**（`launch_persistent_context(user_data_dir=~/.amreview/profile/<域名>/)`）：

- 与日常 Chrome **完全隔离**：独立进程、独立 cookie、独立指纹容器，互不读写
- 两个实例可同时运行（user-data-dir 不同即可并存）
- 登录的是**专用买家小号**，与主力购物账号无任何关联

### 5.2 引导登录流程（一次性）

```
首次使用 / 登录过期时：
  弹出可见窗口（工具自己的浏览器）→ 人工登录小号（验证码随意过）
  → 检测 cookie 出现 at-main / x-main → 自动保存 → 关窗
日常使用：
  headless 带档案静默跑 → 跳回 ap/signin 则标 🍪 提醒重登（通常数周一次）
```

### 5.3 多站点档案

Amazon 账号分区域组（北美 / EU / 印度、澳洲各自独立），**按域名各存一份档案**：

```
~/.amreview/profile/
  ├── amazon.com/      ← 北美小号
  ├── amazon.com.au/   ← 澳洲小号
  └── amazon.in/       ← 印度小号
```

检测链接时按域名自动选用对应档案；未登录的站点先出"待引导登录"提示，不阻塞其他站点。

### 5.4 账号安全边界

20 条/次 + 3~5s/条限速 ≈ 强度远低于人工浏览，对买家号无感。若单站点单日检测量超过 ~500 条，再加代理轮换（预留接口，暂不启用）。

## 六、风险与对策

| 风险 | 概率 | 对策 |
|------|------|------|
| headless 被 edgex guard 识别 | 中 | patchright 自带隐身；仍被拦→换 camoufox（Firefox 深度伪装） |
| 连续访问触发 captcha | 低（20条/次） | 3~5s 限速 + 拦截退避重试 + 被拦截项单独标记人工复核 |
| Amazon 改版换选择器 | 低（data-hook 很稳） | 多选择器 fallback + 未知项截图存档快速暴露问题 |
| 短链/带参数链接格式不一 | 中 | URL 预处理：正则提取 review ID（`/gp/customer-reviews/(\w+)/` 或 `/review/(\w+)/`），统一格式后再访问 |
